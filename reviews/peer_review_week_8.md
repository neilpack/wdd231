## 1. What I Demonstrated Across the Contract

I demonstrated that I can work on a website as part of a team instead of building everything by myself. Our team started a new website that is separate from my hiking guide, and we set up the shared GitHub repository together. We agreed on a project structure with separate folders for pages, styles, scripts, and images so that each person knew where their work belonged and we could avoid editing the same files at the same time.

We managed the project the way a professional team would. We added GitHub rulesets to protect the main branch, so no one could push directly to it and every change had to go through a pull request. Each of us worked on our own branch, made small commits with clear messages, and opened a pull request when a task was ready. We used GitHub Issues to break the work into tasks, and each issue had a definition of done. We also used issues to track defects as we found them, and we closed each one once it was fixed and checked, so we always knew what was finished and what still needed work.

## 2. Evidence I Showed

- **Artifact:** Our shared team repository and the working team website, including the protected main branch with its rulesets, our feature branches, the commit history, our pull requests, and the Issues list with both feature tasks and defects.
- **Test or Verification:** I showed that the main branch ruleset blocks direct pushes and requires a pull request before a change can be merged. I walked through my issues and showed that each task had a definition of done and was checked against it before it was closed. I also showed the defects we found, the pull requests that fixed them, and that each defect was marked as completed. After our branches were merged, I tested the combined site to confirm that the layout was responsive, the controls worked with the keyboard, and there were no console errors.
- **Explanation, Challenge, or Decision:** I explained why we chose to protect the main branch with rulesets instead of letting everyone push directly to it. The rulesets add a small extra step, but they make sure every change is reviewed and that one person's work cannot accidentally break the site for everyone else. I also explained how keeping a clear project structure and small, focused commits made our pull requests easier to review and our merges easier to manage. A challenge was coordinating with teammates whose work depended on mine, which is why we named dependencies and blockers in our progress updates.

## 3. What My Peer Helped Me Notice

Joshua went through each slice with me and confirmed that I had shown all of the criteria in the contract. He helped me notice that our process was much stronger than the website itself. The site we built was very simple, so while it proved that we can use GitHub rulesets, branches, commits, pull requests, issues, and a clear project structure professionally, it did not give us many chances to deal with harder team situations. A larger, more robust project would have more features that depend on each other, more people editing shared files, and more chances for real merge conflicts and integration problems. That would be a better test of whether our process holds up under pressure.

## 4. What I Learned by Asking Questions or Listening

It became clearer to me that working on a team is as much about communication and process as it is about writing code. Tools like rulesets, pull requests, and issues are not just extra steps. They create a record of what was done, why it was done, and who reviewed it, which makes it easier for everyone on the team to trust the main branch. I also learned that tracking defects as issues and closing them only after they are verified is a simple way to make sure problems do not get forgotten. Talking with Joshua helped me see that the value of this process grows as a project gets bigger and more people are involved.
