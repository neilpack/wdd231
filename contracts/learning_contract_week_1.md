Student: Neil Pack

## Primary Competency

My primary competency is **Semantic and accessible HTML**. For this first contract, I am targeting only these parts of that competency:

- I can organize a page with meaningful semantic elements.
- I can create navigation and content that have clear names and a logical order.
- I can move through the main page controls with a keyboard.

I am also working on supporting slices of Responsive CSS and inclusive visual design, JavaScript, the DOM, and events, and project setup. I am not claiming that this contract completes any of those full competencies.

## My Starting Point

I have created simple HTML pages before and can use headings, paragraphs, and links. I can write basic CSS, but I usually adjust margins until the page looks right without checking other viewport sizes. I have used JavaScript examples, but I need more practice connecting an event to a specific DOM update.

## My Learning Plan

First, I will complete the course setup and confirm that the project runs locally. I will then create a page shell for a fictional local hiking guide. It will have a header with the site name, a navigation area, a main section introducing the guide, and a footer with contact information.

I will use the course setup instructions to verify my environment, the DOM practice module to review event handling, the MDN element reference when choosing semantic elements, and the WebAIM checklist to test keyboard access.

I will practice by building the page in this order:

1. Write the semantic HTML structure and meaningful link text.
2. Add mobile-first CSS for readable text, spacing, and a simple wide-screen layout.
3. Add one button that toggles a short navigation panel on narrow screens.
4. Test the page at narrow and wide viewport sizes and with the keyboard.

My first milestone, due **September 11**, is a page that runs locally and includes the semantic structure, visible content, and first mobile layout. I will ask for feedback before spending time on visual polish.

## Evidence of Learning

I will submit or demonstrate:

- A link to my working page and the relevant project files.
- A short explanation identifying the header, navigation, main, and footer and explaining why I chose those elements.
- A screenshot or brief recording showing the page at narrow and wide widths.
- A keyboard test in which I reach the navigation and main interactive control without using a mouse.
- A short explanation of how the button event changes the DOM.
- One problem I encountered, my hypothesis about its cause, the fix I tried, and how I verified the fix.

I will know I am ready for review when:

- The project starts with the documented command and the page loads without console errors.
- The page has a meaningful semantic structure and a logical keyboard order.
- The layout remains readable and usable at both narrow and wide widths.
- I can explain the JavaScript event, the DOM element it changes, and one reason for an HTML or CSS decision without reading an explanation from someone else.

## Support and Risks

The help I may need is a short instructor or peer conversation about choosing semantic elements and debugging the navigation toggle. I will ask for help after I have recorded the expected behavior, actual behavior, and one hypothesis.

My main risk is spending too much time making the page look finished. If that happens, I will stop visual polish, complete the evidence checklist, and ask for feedback on the next smallest improvement.

## AI Use, If Applicable

I may use AI to explain the difference between semantic elements, suggest debugging questions, or give feedback on my accessibility test plan. I will not ask it to produce the complete page.

If I use AI, I will record the question I asked, identify which suggestions I accepted or rejected, and verify the result with the browser, documentation, and keyboard testing. I will be able to explain the final HTML, CSS, and JavaScript without relying on the AI conversation.
