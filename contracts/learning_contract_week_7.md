# Learning Contract: Review SEO and Accessibility

Student: Neil Pack  
Date: October 29, 2026  
Target assessment date: November 5, 2026

## Primary competency

By the end of this contract, I will be able to:

I can audit my hiking guide for SEO and accessibility concerns, make prioritized improvements, and explain how the changes help users and search engines. I can evaluate page metadata, headings, links, images, contrast, focus, reflow, and keyboard access using an evidence-based checklist.

## Specific slices in this contract

- Page titles and meta descriptions
- Heading hierarchy and meaningful link text
- Image alternative text and content structure
- WCAG-informed semantic and visual checks
- Color contrast and visible focus
- Reflow and zoom behavior
- Keyboard-only navigation and interaction

## My starting point

I already know/can:

I can create a semantic HTML page with a language declaration, viewport metadata, a page title, a meta description, headings, navigation, sections, buttons, labels, and a footer. My hiking guide already uses landmarks such as `header`, `nav`, `main`, and `footer`, and it includes a responsive layout, a keyboard-operable menu button, labeled form controls, and live status messages for weather and preference updates.

I still need to learn or improve:

- How to perform a complete SEO and accessibility audit instead of checking only whether the page looks correct.
- How to confirm that the title, description, headings, and links clearly describe the page content.
- How to provide useful alternative text for trail images and identify decorative images correctly.
- How to test color contrast, focus visibility, reflow, and text enlargement.
- How to complete a keyboard-only walkthrough and document any barriers.
- How to prioritize issues by their effect on users and search engines.
- How to connect an improvement to a relevant WCAG principle and verify the result after making the change.

## My learning plan

I will use these resources:

- The [WDD 231 Competency Guide](https://byui-cse.github.io/wdd231-course/), class examples, and feedback from my instructor or a peer.
- The [WebAIM keyboard accessibility checklist](https://webaim.org/techniques/keyboard/).
- The [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) and browser developer tools.
- The [W3C Web Content Accessibility Guidelines](https://www.w3.org/TR/WCAG22/).
- The existing `hike.html`, `hike.css`, and `hike.js` files in my hiking guide.

I will practice by:

I will audit `hike.html` and the related CSS and JavaScript before changing them. I will record the current page title and description, inspect the heading order and navigation link text, check every image for appropriate alternative text, and review whether the HTML structure communicates the content clearly.

I will then test the page with keyboard-only navigation, browser zoom and reflow, a contrast checker, and an accessibility inspection tool when available. I will check that the menu button, preference controls, trail links, and status messages are understandable and usable without a mouse. I will create a prioritized issue list, make the highest-value improvements, and repeat the same checks to compare the results.

My first milestone, due November 1, 2026, is:

I will complete and save a baseline audit checklist for the hiking page. The checklist will include the current results for metadata, headings, links, image alternatives, contrast, focus, reflow, zoom, and keyboard navigation, along with at least three prioritized issues or confirmations.

## Evidence of learning

I will submit or demonstrate:

- A completed before-changes audit checklist or accessibility tool results.
- A prioritized issue list that identifies the most important SEO and accessibility improvements.
- The improved hiking page and any related CSS or JavaScript changes.
- A second audit showing what changed after the improvements.
- A keyboard-only walkthrough covering navigation, the menu button, filters, reset controls, and trail content.
- A contrast, focus, reflow, or zoom test with the result recorded.
- A short explanation of how at least one change relates to a WCAG principle, such as keyboard accessibility, focus visibility, text alternatives, or use of color.
- One documented bug, challenge, or design decision and what I learned from it.

I will know I am ready when:

- The page has a descriptive title and meta description, a logical heading hierarchy, meaningful navigation links, and appropriate image alternatives.
- All important controls and links can be reached and operated with a keyboard, with visible focus and no keyboard trap.
- The page remains usable at narrow widths, when zoomed, and when text is enlarged without losing content or functionality.
- Text and interactive elements meet an appropriate contrast standard, or any exception is documented and corrected where possible.
- I can show before-and-after evidence and explain why each major change improves SEO, accessibility, or both.
- I can identify at least one WCAG principle or success criterion connected to my work.

## Support and risks

The help I may need is:

I may ask a peer or instructor to complete the keyboard walkthrough and review whether the content and link text make sense to someone who did not build the page. I may use browser accessibility tools, WebAIM resources, and the W3C guidelines when I need help interpreting a contrast, focus, semantic HTML, or alternative-text issue.

A risk to my plan is:

A likely obstacle is finding issues that are not obvious from a visual inspection, especially focus problems, low contrast, unclear link context, or missing image descriptions in content generated by JavaScript. I will respond by testing with more than one method, including keyboard navigation, zoom and reflow, a contrast tool, code inspection, and another person's review. I will prioritize changes that remove barriers to using the page rather than changing styles only because I prefer a different appearance.

## AI use, if applicable

I expect to use AI for:

I may use AI for brainstorming audit questions, explaining SEO or WCAG terminology, interpreting tool results, and suggesting possible improvements to semantic HTML, CSS, or keyboard behavior. I will make the final decisions and understand the implementation myself.

I will verify AI suggestions by:

I will compare suggestions with the WDD 231 Competency Guide, WCAG, and WebAIM resources. I will test each accepted change in my own page using code inspection, keyboard navigation, contrast or accessibility tools, and before-and-after checks. I will reject suggestions that are not supported by the guidelines, reduce accessibility, or cannot be verified.
